**Purpose:** RJ asked for TGA sync to keep a tenant's display name in sync with the authoritative `legal_name` returned by training.gov.au — originally raised while investigating an unrelated "Sync Failed" error (see companion audit below), then iterated across four PRs as each fix surfaced the next gap.

---

## What was implemented (across all four PRs)

- **#486** — `TgaIntegrationWizard` (first-time Import) and `TGAIntegrationModal` (Resync/"Sync Now") now compare TGA's `legal_name` against the tenant's current `tenant_name` — exact, case-sensitive match, since TGA's name is authoritative (confirmed with RJ: if TGA's record is all-caps, the tenant becomes all-caps). Any difference triggers a rename. New slug generated via the existing DB function `generate_tenant_slug`, which already handles collisions. Shared logic extracted into `src/lib/tenants/deriveTenantNameUpdate.ts` since both sync paths needed identical behaviour.
- **#488** — Discovered `tenants.name` is a **separate** legacy column from `tenant_name`, and the sidebar/nav actually reads `name`, not `tenant_name`. `deriveTenantNameUpdate` extended to also set `name` alongside `tenant_name`.
- **#489** — Discovered the DB write was correct but nothing told the *app* to notice: `AppContext.activeTenantName` (read by every sidebar variant — Admin, SSO, RoleBased, EnhancedRole — plus impersonation/support-mode chrome) only reloads on `SIGNED_IN`/`INITIAL_SESSION`/`TOKEN_REFRESHED`, and the tenant-switcher dropdown's own React Query cache (`useTenantSwitcherData`) had no reason to refetch either. Added `AppContext.refetchContext()` (re-runs `get_my_app_context`, re-applies in place) and wired it plus a `tenant-switcher-data` cache invalidation into both Import and Resync success paths.
- **#491** — Found the actual root cause of persistent staleness: `deriveTenantNameUpdate` only ever compared the new legal name against `tenant_name` to decide whether *anything* needed renaming, then wrote both columns together if it fired. Once `tenant_name` had already self-corrected in an earlier sync (from #486, before #488 existed), that single-column comparison always read "unchanged" on every later sync — permanently skipping `name`, which had never actually been touched, even though `get_my_app_context()` (confirmed via live `pg_get_functiondef`, not a migration-file guess) joins on `tenants.name` specifically. Fixed by comparing both columns independently — either one drifting now triggers the correction.

## Blast radius

`src/lib/tenants/deriveTenantNameUpdate.ts` (new), `src/components/admin/TgaIntegrationWizard.tsx`, `src/components/admin/TGAIntegrationModal.tsx`, `src/contexts/AppContext.tsx` (new `refetchContext()` export, additive — no existing consumer signature changed). No route or role-guard changes. No new DB writes beyond `tenants.tenant_name`/`name`/`slug`, which the sync flow already had permission to write.

No migrations in any of the four PRs — reuses the existing `generate_tenant_slug` DB function and existing columns. `tenants.slug` confirmed (via `AppRoutes.tsx` + full `.eq('slug'...)` search) to be unused in frontend routing, so renaming it live carries no risk of breaking a bookmarked URL.

## Related, separately-flagged issues found during this work — NOT fixed here

These surfaced while diagnosing the original "Sync Failed" report and are deliberately out of scope for the above PRs:

1. **`trg_protect_demo_identity`** — a live production trigger on `public.tenants` (confirmed via `pg_get_triggerdef`, **not present in any git migration file** — a real instance of the untracked-drift problem this repo's migration docs warn about) silently reverts `legal_name`/`tga_last_synced_at`/and 14 other identity fields on any `UPDATE` whenever `tenants.is_demo = true`, unless a session variable (`complyhub.allow_demo_identity_write`) is set to `'on'` — which nothing in the app currently does. This blocks TGA sync entirely for any `is_demo = true` tenant, silently (no error, works identically regardless of role/RLS). `is_demo` is itself documented as `@deprecated Use tenant_type = 'trial' instead` in its own column comment, so the trigger is gated on a column the schema says shouldn't be relied on. **Flag for Dave** — decide whether the trigger should check `tenant_type` instead, or whether tenant-creation flows should stop setting `is_demo = true` for genuine trial signups.
2. **Duplicate tenant records for one real business.** Confirmed two separate, unlinked `tenants` rows exist for what appears to be the same prospect ("Positive Training Academy Pty Ltd", created 29 Jul by Dave via a manual/demo path, `is_demo = true`; and "Harry Ragavanis's Organization (Trial)", created 11 Aug by Angela via the `JoinRequestsTab` → `create_tenant_only` staff-triage flow) — created independently, 13 days apart, with no way for either person to know the other tenant already existed. This is what caused the original RTO-ID unique-constraint collision that started this whole investigation. **Not resolved** — needs a decision on which tenant is canonical and what happens to the other, plus input from Dave/Angela since they each independently created one.
3. **No tenant-creation path checks for an existing tenant** by RTO ID, company name, or email domain before creating a new one — confirmed across `admin_create_trial_tenant_for_user`, `create_tenant_only`, `create_trial_tenant`, and the self-service demo/trial signup flows (`DemoSignup.tsx`, `demo_signup_admin` edge function, `src/lib/demoSignup.ts`). The existing "Scan Duplicates" tool (`ScanDuplicatesDialog.tsx`, `JoinRequestsTab.tsx`) only checks for duplicate *signup requests* against existing user accounts, not duplicate *tenants* — this class of problem is currently invisible to any existing tooling. **Flagged, not actioned.**
