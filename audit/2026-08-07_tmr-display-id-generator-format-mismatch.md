## Why this looked like a repeat of the 31 July fix, and wasn't

Same symptom, same friendly error message, same underlying constraint
(`trainer_monthly_reports_tenant_id_display_id_key`), same function (`tmr_next_display_id`) — so
the first hypothesis was that the 31 July advisory-lock fix had regressed or never actually
deployed. RJ explicitly asked for certainty rather than a plausible guess, so both were checked
live rather than assumed:

- `git log -S "tmr_next_display_id"` — untouched since the 31 July fix commit. No reversion.
- `pg_get_functiondef('public.tmr_next_display_id(uuid)')` run by RJ directly (Claude was blocked
  by Claude Code's own safety classifier from reading this on production) — matched the git file
  byte-for-byte. The advisory lock is genuinely live.

That ruled out the obvious theory. It also matters mechanically: `pg_advisory_xact_lock` under
Postgres' default READ COMMITTED isolation should make a *retry* succeed almost always after a
single collision, once the lock is confirmed genuinely live — a real concurrency race repeating
identically across both the original attempt and its automatic retry would be an unlikely
compound event. That mismatch between "lock confirmed live" and "both attempts failed identically"
is what pointed at a deterministic bug instead of a race.

## Root cause — confirmed against live data, not inferred

RJ ran a read query against `trainer_monthly_reports` for the affected tenant
(`bc515b64-d24f-4e9d-811b-1f5c0f62a3f7`, Vivacity Testing Tenant). All three existing rows were
generated by the *other* divergent `display_id` generators the 31 July audit already documented as
unreconciled (three independent write paths, three different formats) — none by this trigger's own
counter:

| display_id | regex_extract (`SUBSTRING(display_id FROM 'TMR-(\d+)')`) |
|---|---|
| `TMR-20260408-JH35` | `20260408` |
| `TMR-20260402-CTZP` | `20260402` |
| `TMR-2026` | `2026` |

The old pattern was unanchored, so it matched digits anywhere after `TMR-`, not just this
generator's own `TMR-####` shape. `MAX(20260408, 20260402, 2026) = 20260408`, next = `20260409`,
then:

```sql
LPAD(20260409::text, 4, '0')
```

Postgres' `lpad` only pads when the input is *shorter* than the target length — when longer, it
**truncates to the leftmost N characters** rather than erroring or returning the full value. `'20260409'`
is 8 characters against a target of 4, so this returned `'2026'`, not `'20260409'`. Result:
`'TMR-2026'` — the exact row that already existed (created 31 Jul 2026, almost certainly the first
time this exact computation fired and had nothing to collide with yet).

Because the three source values never change, this computation is **100% deterministic**: every
insert attempt for this tenant via this trigger — original and retry alike — recomputes the
identical `'TMR-2026'` and collides with the identical row, regardless of who submits or how many
times it retries. This is why "different user" and "we already tried to fix this" both looked true
at once — the fix from 31 July was real and correctly deployed, it just couldn't fix a wrong answer
by serializing access to it.

On "multi-role user" (RJ's original lead): checked for any connection between role/multi-tenancy
and duplicate submission in the frontend file — found none. No evidence it was causal; treated as
an incidental detail about the reporting account, not a contributing factor.

## What was fixed

`tmr_next_display_id()`, `CREATE OR REPLACE`:

1. **Anchored the regex** — `'^TMR-(\d+)$'` instead of `'TMR-(\d+)'` — so only this generator's own
   whole-string format is ever considered. The other generators' formats
   (`TMR-YYYYMMDD-XXXX`, `TMR-YYYYMM-xxxxxx`) no longer match at all.
2. **Guarded the `LPAD` call** — `LPAD(v_next_num::TEXT, GREATEST(4, LENGTH(v_next_num::TEXT)), '0')`
   instead of a hardcoded `4`. Same failure shape as the root cause, just latent until a tenant's
   real count passes 9999 — fixed defensively in the same pass since it's the same line of code
   already being changed, not scope creep.
3. **Data reconciliation** — renamed the one poisoned row's `display_id` from `'TMR-2026'` to
   `'TMR-2026-LEGACY'` (guarded by both `id` and the exact prior value, idempotent). Not deleted —
   it's a real report with real trainer data, just an artifact identifier. Renamed rather than
   given a "correct" sequential value, since inventing what it "should" have been isn't something
   that could be confirmed with certainty.

The advisory lock itself was left untouched — already confirmed live and correct; this was never a
concurrency problem.

## Deliberately not fixed here (scope)

`submit_trainer_monthly_report`'s 8 inline register-id generators (`ssr_register`, `whs_register`,
`ofi_register`, `risk_register`, `rpl_register`, `caa_register`, `pdr_register`, `ien_register`)
have the identical `LPAD(v_seq::text, 4, '0')` truncation shape and could theoretically hit the same
failure once any of those counters passes 9999. Not touched — not implicated in this specific bug,
and reconciling the underlying three-divergent-generator problem across all of
`trainer_monthly_reports` and these 8 tables is the same "separate, larger reconciliation" already
flagged in the 31 July audit, not something to fold into an urgent point fix.
