# Manual CI deploys — active as of 09 July 2026

> Moved from `CLAUDE.local.md` (10 July 2026). Content unchanged from the original. **This section is explicitly temporary — remove/rewrite once CI minutes are optimized (see last line).**

The org billing issue from early July is resolved — GitHub Actions runs again. This is now a deliberate choice: CI workflows on `rto-compass-hub` are being run manually / selectively disabled because they currently burn too many Actions minutes per run, and that needs to be optimized before leaving everything on full auto-pilot again. Until that optimization work happens, treat CI as **assist, not autopilot** — verify what a workflow actually did rather than assuming a merge alone finished the job.

**Edge functions:** deploy manually to production via the Supabase MCP `deploy_edge_function` tool, using the exact file content already committed on `main` — never anything uncommitted. Same safety rule as before: commit to `main` first, always, then manually deploy exactly that committed content — a manual deploy of already-committed code is a no-op if/when CI later redeploys the same thing, not a regression.

**Migrations:** a new `Apply pending migrations to production` GitHub Actions workflow appeared on 09 July (post-billing-fix) that runs `supabase db push` on every merge to `main`. It failed on its first real run (PR #158 merge, commit `7aec34d8f`) with the same `Remote migration versions not found in local migrations directory` error the CLI throws whenever it walks past the ~3,800 archived Lovable-era files in `supabase/migrations/_archive/` — `supabase db push` treats that as fatal, unlike the branch-DB-creation flow which only warns. Brian disabled this workflow after that failure. **Migrations are back to the manual-apply flow for now:** merge PR → manually run `apply_migration` via Supabase MCP for whatever `.sql` files landed → verify the object changed in production. Do not re-enable `Apply pending migrations to production` until either the archive-directory issue is resolved (e.g. moving `_archive/` fully out of `supabase/migrations/` so the CLI never walks it) or the workflow is changed to tolerate/ignore that specific warning the way branch creation does.

**Remove/rewrite this section once CI minutes are optimized and both the edge-function and migration-apply workflows are confirmed reliable enough to leave on auto-pilot.**
